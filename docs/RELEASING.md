# Releasing RuDo

Pushing a version tag such as `v1.0.0` builds and publishes the GitHub release automatically:
binaries for every supported system, `.deb`, `.rpm` and Arch packages, SHA-256 checksums,
install scripts, release notes from the changelog, an updated Homebrew formula and a Docker
image. The workflow, `.github/workflows/release.yml`, is generated by
[dist](https://axodotdev.github.io/cargo-dist) from `dist-workspace.toml`.
Publishing on crates.io stays a manual step.

## Once, before the first release

The Homebrew job pushes the formula `rudo-tui.rb` to a tap repository and needs a token that
may write to it.

1. Create the public repository `Altrabeth/homebrew-tap` on GitHub with a README, so that it
   has a default branch; the job adds `Formula/rudo-tui.rb`. Users install with
   `brew install altrabeth/tap/rudo-tui`.
2. Create a fine-grained personal access token (**Settings, Developer settings, Personal
   access tokens, Fine-grained tokens**): resource owner `Altrabeth`, repository access
   **Only select repositories** with `Altrabeth/homebrew-tap`, repository permission
   **Contents: Read and write** (Metadata read-only is added by GitHub). Note its expiry date;
   a release after it fails in the Homebrew job until the token is renewed.
3. In `Altrabeth/RuDo`, **Settings, Secrets and variables, Actions**, add the repository
   secret `HOMEBREW_TAP_TOKEN` with the token.

The other jobs use the `GITHUB_TOKEN` of the workflow, which `release.yml` grants
`contents: write` to create the release and the Docker job `packages: write`.

After the first release, the package `rudo-tui` exists on the GitHub Container Registry but is
private, because packages pushed with `GITHUB_TOKEN` start private. Make it public once: on the
package page (**Altrabeth, Packages, rudo-tui, Package settings**), **Change visibility** to
public, so that `docker pull ghcr.io/altrabeth/rudo-tui` works without logging in. The label
`org.opencontainers.image.source` links the package to the repository, whose Actions then keep
write access to it.

## Release procedure

1. Choose the version by [Semantic Versioning](https://semver.org/spec/v2.0.0.html).
2. In `CHANGELOG.md`, move the entries of `[Unreleased]` into a section
   `## [X.Y.Z] - YYYY-MM-DD` dated today, and leave an empty `[Unreleased]` above it. dist
   takes the release notes from the section whose heading names the tag's version; relative
   links in it, such as `README.md`, do not resolve on the release page, so write them as full
   URLs.
3. Set `version = "X.Y.Z"` in `Cargo.toml` and run `cargo check` to update `Cargo.lock`.
4. Run `just check`, `just smoke`, `just test-musl`, `just docker-smoke`, `just publish-dry-run`
   and `dist plan`, which lists the archives of the release; `dist plan --output-format=json`
   shows the release notes in `announcement_github_body`. Install dist from its
   [release](https://github.com/axodotdev/cargo-dist/releases) at the version of
   `cargo-dist-version` in `dist-workspace.toml`.
5. Run the manual checklist in [`docs/QA.md`](QA.md) and commit the filled-in copy to
   `docs/qa/`.
6. Commit (`chore: release X.Y.Z`), merge into `main` and wait for CI, including the jobs for
   Windows, macOS and FreeBSD that run on `main`.
7. Tag the merge commit on `main` and push the tag:

   ```sh
   git tag -a vX.Y.Z -m "RuDo X.Y.Z"
   git push origin vX.Y.Z
   ```

8. When the release workflow has succeeded, publish the crate: `cargo publish --locked`.
9. Update the packaging recipes with `just packaging-update X.Y.Z`, commit them and submit
   them to the AUR, Copr, OBS, GURU, winget and Chocolatey as described in
   [`docs/PACKAGING.md`](PACKAGING.md).

A version with a pre-release suffix (`v1.1.0-rc.1`) becomes a GitHub pre-release and does not
update the Homebrew formula or push a Docker image. Its Linux packages carry the version in
the syntax of their format, `1.1.0~rc.1` in the `.deb` and `.rpm` and `1.1.0rc1` in the Arch
package, so that it sorts before `1.1.0` (see
[`PACKAGING.md`](PACKAGING.md#versions-of-pre-releases)). If a build job fails, nothing is
published: fix the cause, delete the tag locally and on GitHub, and tag again. If only
`publish-homebrew-formula` fails, the release exists; fix the token and re-run the failed job.
The same holds for `custom-publish-docker`.

## What runs automatically

`release.yml` runs `dist plan` on every pull request, which checks the configuration without
building. On a tag it runs these jobs:

| Job                         | What it does                                                           |
| --------------------------- | ---------------------------------------------------------------------- |
| `plan`                      | computes the release from the tag, `Cargo.toml` and the changelog      |
| `build-local-artifacts`     | builds the `dist` profile on one runner per target, packs the archives |
| `build-global-artifacts`    | install scripts, Homebrew formula, source archive and `sha256.sum`     |
| `custom-build-freebsd`      | the FreeBSD archive (see below)                                        |
| `custom-build-vendor-tarball` | the vendor archive of the crates for offline package builders        |
| `custom-build-linux-packages` | `.deb`, `.rpm` and Arch packages (see below)                         |
| `host`                      | creates the GitHub release with the notes and uploads every file       |
| `publish-homebrew-formula`  | commits `Formula/rudo-tui.rb` to `Altrabeth/homebrew-tap`              |
| `custom-publish-docker`     | pushes the Docker image to `ghcr.io/altrabeth/rudo-tui` (see below)    |
| `announce`                  | finishes the release                                                   |

The release contains, for each target, `rudo-tui-<target>.tar.xz` (`.zip` for Windows) with
`rudo`, `README.md`, `LICENSE` and `CHANGELOG.md`, and a `.sha256` file next to it:

| Target                       | Runner             | Notes                                     |
| ---------------------------- | ------------------ | ----------------------------------------- |
| `x86_64-unknown-linux-gnu`   | `ubuntu-22.04`     | glibc 2.35 or newer                       |
| `aarch64-unknown-linux-gnu`  | `ubuntu-22.04-arm` | glibc 2.35 or newer                       |
| `x86_64-unknown-linux-musl`  | `ubuntu-22.04`     | static, with the time zone database       |
| `aarch64-unknown-linux-musl` | `ubuntu-22.04-arm` | static, with the time zone database       |
| `x86_64-apple-darwin`        | `macos-15-intel`   | not notarized                             |
| `aarch64-apple-darwin`       | `macos-15`         | not notarized                             |
| `x86_64-pc-windows-msvc`     | `windows-2022`     | the archive has no folder inside          |
| `x86_64-unknown-freebsd`     | FreeBSD 14.4 VM    | custom job, not in `sha256.sum`           |

Besides the archives: `rudo-tui-installer.sh` and `rudo-tui-installer.ps1`, which install
into `~/.cargo/bin`; `rudo-tui.rb`, the formula; `source.tar.gz`; `sha256.sum` with the
checksums of everything dist built; and `rudo-tui-X.Y.Z-vendor.tar.xz` with its `.sha256` file,
the crates of `Cargo.lock` for the RPM spec, which builds without network; and the Linux
packages described below.
`.github/workflows/build-vendor-tarball.yml`, a custom global artifacts job like the FreeBSD one,
builds it with `just vendor-tarball`; it is not in `sha256.sum` either. `cargo binstall
rudo-tui` finds the archives through `[package.metadata.binstall]` in `Cargo.toml`, which must
keep matching the archive names.

The musl targets depend on jiff with `tzdb-bundle-always` (a target-specific dependency in
`Cargo.toml`), because static binaries often run where `/usr/share/zoneinfo` is missing.
`tests/time_zone.rs`, run by `just test-musl`, checks that the database is bundled, and
[`docs/QA.md`](QA.md) checks the fallback of the released binary.

## FreeBSD

dist has no FreeBSD target, so `dist-workspace.toml` adds the reusable workflow
`.github/workflows/build-freebsd.yml` as a custom global artifacts job. It builds the `dist`
profile in a FreeBSD 14.4 virtual machine (`vmactions/freebsd-vm`, pinned like in `ci.yml`)
and packs `rudo-tui-x86_64-unknown-freebsd.tar.xz` like the other archives, with its `.sha256`
file; `host` uploads it with the rest. Built on 14.5 or later, the file watcher would use
inotify, which fails on older releases, so keep the virtual machine at 14.4 until 14.4 is no
longer supported. The install scripts and the Homebrew formula do not know the FreeBSD
archive; `cargo binstall` does.

## Linux packages

dist builds no native Linux packages, so `dist-workspace.toml` adds the reusable workflow
`.github/workflows/build-linux-packages.yml` as a custom global artifacts job, which runs once
the archives exist. Its files and their `.sha256` files are not in `sha256.sum`:

- `rudo-tui_X.Y.Z-1_amd64.deb` and `rudo-tui_X.Y.Z-1_arm64.deb`, built by `cargo deb` from
  `[package.metadata.deb]` in `Cargo.toml`;
- `rudo-tui-X.Y.Z-1.x86_64.rpm` and `rudo-tui-X.Y.Z-1.aarch64.rpm`, built by
  `cargo generate-rpm` from `[package.metadata.generate-rpm]`;
- `rudo-tui-X.Y.Z-1-x86_64.pkg.tar.zst`, built by `makepkg` from
  `packaging/aur/rudo-tui/PKGBUILD`.

The `.deb` and `.rpm` packages hold the static binary of the `*-linux-musl` archives, unpacked
after its checksum is verified, so they hold the same bytes as the archives. A static binary
needs no particular glibc, so one package installs on old releases such as Debian oldstable,
Ubuntu LTS or RHEL-like systems as well as on the newest, and it depends on nothing; it also
carries the time zone database, but prefers the system's. Both put `rudo` into `/usr/bin/`
and the README and changelog into `/usr/share/doc/rudo-tui/`; the `.deb` puts `LICENSE` there
too, the `.rpm` into `/usr/share/licenses/rudo-tui/`. Name, version, description and license
come from `[package]` in `Cargo.toml`. Both declare a conflict with a package `rudo`, an
unrelated program with the same command. `just linux-packages <target>` packs the binary that
`cargo build --profile dist --target <target>` left in `target/<target>/dist/`; the two cargo
subcommands are installed with `cargo install --locked cargo-deb cargo-generate-rpm`.

The Arch package is built with `just package-arch` from the PKGBUILD of the AUR, in an
`archlinux:base-devel` container, from a `git archive` of the tagged commit with the version
of `Cargo.toml`, because the PKGBUILD names the previous release until
`just packaging-update` runs after the release. It is built with the distribution's toolchain
and linked to its glibc, so it is for current Arch Linux only.

Before the upload, `scripts/package-smoke.sh` installs every package in a container of its
distribution (`debian:stable`, `fedora:latest`, `opensuse/tumbleweed`, `archlinux`; arm64
containers run under QEMU), runs `rudo --version` and `rudo config check`, and removes it
again. `just package-smoke` runs it locally on every package in `target/distrib/` with Docker.
The `deb-rpm` and `arch` jobs of `.github/workflows/packaging.yml` build and test the same
packages from every push, the `.deb` and `.rpm` natively on x86_64 and aarch64 runners.

## Docker image

dist has no Docker support, so `dist-workspace.toml` adds the reusable workflow
`.github/workflows/publish-docker.yml` as a custom publish job, which runs once the release
exists and gets `packages: write` through `github-custom-job-permissions`. It builds the
`Dockerfile` of the tagged commit with buildx for `linux/amd64` and `linux/arm64`, runs
`scripts/docker-smoke.sh` on the amd64 image (`--version`, `config check` and the hint
without a terminal) and pushes both under the tags `X.Y.Z` and `latest`, with OCI labels and
annotations for source, revision, version and license. The `docker` job of `ci.yml` runs the
same smoke test on every push; `just docker-smoke` runs it locally.

The `Dockerfile` compiles the static musl binary itself, with the `dist` profile, so the image
holds the same kind of binary as the `*-linux-musl` archives, including the time zone
database, on `scratch`. Its build stage runs on the platform of the build machine and
cross-compiles with `rust-lld`, which needs no emulation as long as RuDo has no C
dependencies. When `rust-toolchain.toml` moves to a new Rust version, update the tag of the
`rust` image and `RUSTUP_TOOLCHAIN` in the `Dockerfile` with it.

## Changing the release workflow

Do not edit `release.yml` by hand: change `dist-workspace.toml` and run `dist generate`. To
update dist, install the new version and run `dist init --yes`, which also regenerates the
workflow. dist names the actions it uses by tag; `[dist.github-action-commits]` pins them to
commits, so update those to the commits of the versions that the new dist uses. Check the
workflows with [actionlint](https://github.com/rhysd/actionlint); `.github/actionlint.yaml`
silences its error for the `uses: $/...` syntax of dist until actionlint supports it.

The workflow cannot be tried before the repository is on GitHub and a tag is pushed. Pull
requests run its `plan` job; the first tag runs it completely.
